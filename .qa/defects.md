**SEVERITY:** P3 (Low) — audit-integrity gap, not a data-access breach
**COMPONENT:** `server/routers/b2b.ts:162-172` (`approvePurchaseOrder`)

**RECOMMENDED FIX:** Derive `approvedBy` from `ctx.user.id`/`ctx.user.name` server-side; drop it from the input schema.
**STATUS:** ✅ FIXED. `approvedBy` removed from the input schema; the mutation now sets `approvedBy: String(ctx.user.id)` derived from the authenticated session (`server/routers/b2b.ts:162-172`), matching the pattern already used for `writeAuditLog` actor fields elsewhere (e.g. `escrow.ts`). ## QA-005 — Trade-credit facility approval/modification bypassed the finance-role gate; any tenant staff member (including read-only "analyst") could extend or freeze real credit exposure
**SEVERITY:** P1 (High) — real financial-exposure authorization gap, matches a failure mode the codebase's own security model (W46) was explicitly built to close elsewhere, but this router was missed
**COMPONENT:** `server/routers/tradeCredit.ts` — `createAccount`, `updateAccount`, `setAccountStatus`, `approveAccount`, `recordRepayment`
**EVIDENCE:**
- `server/services/capabilities.ts` header (W46 kyc / TEN-9), quoted verbatim: *"The 3-role model (owner/operator/analyst) let ANY operator move money."* — describing exactly the bug class this fix exists to prevent — and: *"moneyProcedure + assertMoneyAccess admit the scoped 'finance' role; 'catalog'/'analyst' can NEVER move money."*
- `assertTenantAccess` (`server/_core/trpc.ts:146-164`) checks only tenant **membership** (any role) — it has no role-level check at all. Confirmed by reading its full body: admin bypass → `user.tenantId === tenantId` → `user.memberships.includes(tenantId)` → FORBIDDEN. No `membership.role` check anywhere in that function.
- All 5 procedures above call bare `assertTenantAccess(ctx.user, input.supplierTenantId)` before creating a facility with a real `limitCents`, activating a pending facility, changing its limit/terms, freezing/closing it, or recording a repayment against the outstanding balance — meaning an "analyst" (read-only-intended) or "catalog" (product-only-intended) membership at the supplier tenant could call any of these directly via tRPC and it would succeed.
- Compare to `escrow.ts confirmDelivery`, which was hardened for precisely this reason (its own comment: *"an ANALYST membership is not enough (owner|operator or admin; assertTenantAccess was role-agnostic)"*) — that fix was never applied to this router.
- The router's own header comment claimed *"every procedure is gated by assertTenantAccess"* and described only tenant isolation, never role scoping — confirming this wasn't a typo/oversight in one call site but the file's original design predating the W46 capability model.
**IMPACT:** A compromised or careless low-privilege staff account at a supplier tenant (analyst/catalog role — roles explicitly documented elsewhere as forbidden from money movement) could open a credit line to a buyer, raise an existing limit, unfreeze a suspended facility, or record a fabricated repayment, all without ever touching the money-gated procedures the rest of the platform relies on.
**FIX APPLIED:** Swapped `assertTenantAccess` → `await assertMoneyAccess` (owner|operator|finance only) on the 5 supplier-side procedures that create/modify real exposure. Left buyer-side self-service procedures (`requestAccount`, `requestMandate`, `confirmMandate`, `revokeMandate`, `initiateRepayment`) on `assertTenantAccess` — those act on the caller's own tenant's exposure, not a counterparty's, and over-restricting them wasn't verified as necessary or safe in the time available; flagging `initiateRepayment` in particular as a lower-priority candidate for the same treatment if you want full consistency, since it does move money (charges a mandate / creates a payment link), just in the safer direction (paying down debt, not creating it).
**REGRESSION:** Found 2 tests in `server/tradeCredit.kybGate.test.ts` broke on the fix — not because the fix was wrong, but because that test file's `fakeDb()` mock answers every table query with the same in-memory array, so `assertMoneyAccess`'s new `tenant_memberships` lookup was misanswered with an unrelated KYC row. Fixed by mocking `getMembership` to return `null` (the correct "no membership row, fall back to the legacy `users.tenantId` shortcut" case, matching what that test fixture already models). All 8 related test files (138 tests) pass; `authzCoverage.test.ts`'s ratchets (guard-count ≥115, scanned-procedure count ≥630) still hold — `assertMoneyAccess(` is already recognized as a valid guard by that scanner's generic `assert\w*Access\(` pattern. `tsc --noEmit` clean. Full-suite regression re-run in progress to confirm no other breakage.
**STATUS:** ✅ Fixed, verified on targeted + related suites AND full regression (261/261 files, 3929 passed/7 skipped/0 failed).

## QA-007 — Gift-card `adjust` had no real idempotency protection, contradicting the file's own documented invariant and every sibling money path in the same file
**SEVERITY:** P2 (Medium) — real double-application risk on retry, bounded by this being a manual/back-office tool rather than a high-frequency automated flow
**COMPONENT:** `server/services/giftCards.ts` `adjustGiftCard` (called by `server/routers/giftCards.ts` `adjust`, the same procedure fixed for role-scoping in QA-006)
**EVIDENCE:**
- File header doctrine, quoted verbatim (`server/services/giftCards.ts:9-11`): *"every money-moving leg writes a gift_card_transactions row whose idempotency_key is UNIQUE — the insert IS the exactly-once claim, so webhook replays / chat retries never double-credit or double-debit."*
- Confirmed the unique index is real: `drizzle/schema.ts:6063` `uniqueIndex("gift_card_tx_idempotency_uidx").on(t.idempotencyKey)`.
- Every OTHER money-moving function in this exact file derives a **deterministic** key tied to the underlying transaction: `purchaseGiftCard` → `` `giftcard-purchase:${reference}` `` (line 132), `redeemGiftCard`/checkout path → `giftCardRedeemKey(orderId, code)` (deterministic, lines 330/350), `issueGiftCard` → `` `issue:${id}` `` (line 427).
- `adjustGiftCard` (the odd one out) generated `` `adjust:${crypto.randomUUID()}` `` — a **fresh random value on every call** (was at line 497 before the fix). This makes the unique index structurally incapable of catching a duplicate: two calls with identical `{tenantId, code, deltaCents, note}` (e.g. a network-timeout retry, or a double-click in the admin portal) get different random keys, both inserts succeed, and `balance_cents` is incremented/decremented twice.
**IMPACT:** A retried or double-submitted manual gift-card adjustment silently applies the delta twice — no error, no rejection, the exact failure mode the file's own doctrine comment says should be impossible.
**FIX APPLIED:** `adjustGiftCard` now accepts an optional `idempotencyKey` (threaded through from a new optional `idempotencyKey` field on the router's `.input()`, mirroring the existing pattern in `escrow.ts createHold`/`requestWithdrawal`). When supplied, a matching existing `gift_card_transactions` row short-circuits the whole mutation and returns the current (already-adjusted) balance instead of re-applying — checked inside the same row-locked transaction as the balance update, so it's race-safe. When NOT supplied, behavior is unchanged from before (random key, no protection) — deliberately not inventing an unsafe default, since two *legitimately* distinct adjustments could coincidentally share the same `{tenantId, code, deltaCents, note}` and a content-based default key would wrongly dedupe them. This puts the same tool in callers' hands that `escrow.ts` gives its callers; closing the gap fully would mean deciding whether the admin-portal UI should always generate and resend a stable key per submit action, which is a UI-side follow-up, not a server-side one.
**VERIFICATION:** `tsc --noEmit` clean. **Not** covered by a new automated test — this function uses raw `sql` tagged-template `tx.execute()` calls inside `db.transaction()`, a style with no existing unit-test mocking pattern in this repo (grepped for one, found none), and a mock couldn't prove the real unique-constraint collision behavior this fix relies on anyway (that needs a live Postgres). Flagging as a good candidate for `scripts/pg-integration-money-paths.ts` or the dockerized e2e suite once real infra is available — logged as a testing gap, not silently skipped.
**STATUS:** ✅ Fixed (code + typecheck verified); integration-level proof deferred to when Postgres/Docker is available.

## QA-008 — `scripts/run-e2e.sh` crashes immediately on macOS with `--no-ml` (or with no extra vitest args): "unbound variable"
**SEVERITY:** P2 (Medium) — the canonical e2e entry point (`docs/E2E.md` calls this "Running — Docker path (canonical)") was unusable on macOS in its documented `--no-ml` form, and would also have broken on the plain default invocation with no trailing vitest args
**COMPONENT:** `scripts/run-e2e.sh`
**EVIDENCE:**
- Reproduced directly: `scripts/run-e2e.sh --no-ml` failed immediately at the `docker compose build` step with `scripts/run-e2e.sh: line 62: PROFILES[@]: unbound variable`.
- Root cause: the script has `set -uo pipefail` (line 12). `PROFILES=()` when `--no-ml` is passed (line 18 default `WITH_ML=1` → `PROFILES=(--profile ml)`; `--no-ml` sets `WITH_ML=0`, leaving `PROFILES` empty). `"${PROFILES[@]}"` on an **empty** array under `set -u` throws "unbound variable" on bash ≤4.3 — confirmed the system `/bin/bash` here is `3.2.57(1)-release`, Apple's frozen build (GPLv2 licensing freeze since ~2007; never upgraded past 3.2). The bug was fixed in bash 4.4 (2016), so this only manifests on macOS's default shell, not Linux CI runners — which is presumably why it was never caught.
- Same pattern present a second time: `VITEST_ARGS` (line 20) also starts as `()` and stays empty on any invocation with no trailing `-- <args>` (i.e. the plain, most common invocation `scripts/run-e2e.sh` or `scripts/run-e2e.sh --no-ml` with nothing after) — `"${VITEST_ARGS[@]}"` at the two `vitest run` call sites (then lines 117/120) would have hit the identical crash one step later even after fixing the first occurrence.
**IMPACT:** Anyone running the documented canonical e2e command on a stock macOS machine (no custom bash install) gets an immediate, confusing crash with no useful error about *why* — `docker compose build` never even starts. This is exactly the path this session needed to actually exercise the funds-flow concurrency invariants.
**FIX APPLIED:** Standard bash 3.2-safe idiom for "expand an array that might be empty under `set -u`": `${ARR[@]+"${ARR[@]}"}` instead of `"${ARR[@]}"`. Applied at all 4 call sites (`PROFILES` ×2, `VITEST_ARGS` ×2). `bash -n` confirms valid syntax; behaviorally identical to the original on a modern bash (Linux CI unaffected either way).
**STATUS:** ✅ Fixed.

## QA-018 — P2 (hardening): server-initiated OAuth flow had no PKCE and never verified its nonce

## QA-020 — P2 → FIXED: the SPA's primary login had no PKCE and no working CSRF/nonce binding — login CSRF, plus an open redirect found on the way
**COMPONENT:** `client/src/const.ts` `startLogin()` (used by the merchant SPA and the platform-admin / tenant-portal apps), callback in `server/_core/oauth.ts`
**EVIDENCE:**
- The code and its JSDoc claim PKCE ("Generate PKCE code verifier and challenge"), but only a `codeVerifier` is generated and parked in `sessionStorage`; **no `code_challenge` is ever added to the authorization URL** and the verifier never reaches the server, so no PKCE happens.
- The CSRF/nonce binding cookie is `__Host-oauth_state`, set with `document.cookie = "__Host-oauth_state=…; Path=/; Max-Age=600; SameSite=Lax"` — **no `Secure` attribute**, and browsers reject `__Host-`-prefixed cookies without it, so it is most likely never stored on https. Independently, `grep` shows the server **never reads** `OAUTH_STATE_COOKIE` (only `shared/const.ts` defines it), and `decodeOAuthState` is used solely to recover `returnTo`.
- Net effect: nothing binds the callback to the browser that started the login, so an attacker who completes a login at Keycloak can hand the victim a crafted `/api/auth/callback?code=…&state=…` link and get the victim's browser signed in **as the attacker** (login CSRF). Severity is moderate (victim ends up operating inside an attacker-owned account rather than the attacker taking over the victim's), and it is the classic case PKCE/state-binding exists to close.
**WHY NOT FIXED HERE:** the correct fix changes the primary login path for three front-ends (set `Secure`, send a real challenge, carry the verifier to the server, enforce state==cookie server-side), and I cannot exercise that flow against a real browser + Keycloak in this environment (UI/browser testing is a documented tooling gap). Breaking login for everyone to close a moderate-severity CSRF without being able to test it would be the wrong trade. **Recommended fix:** switch `startLogin()` to navigate to the server-driven `GET /api/auth/login?redirect=<returnTo>` (which now does PKCE + signed-cookie state + nonce) after confirming multi-origin `redirect_uri` handling for the portals, and test with a real browser. Inaccurate JSDoc corrected so nobody keeps believing PKCE exists there.

**FIXED (2026-09-21) — the original note's reason for not fixing it was "cannot test a browser + Keycloak flow"; what changed is that the property that matters lives on OUR side of that boundary and is testable there.** The real bug was not only the client. `/api/auth/callback` *ignored* a missing, tampered, expired or wrong-state transaction cookie and exchanged the code anyway, and `oauthPkce.test.ts` pinned that as "unchanged behaviour". Fixing only the client (as the original recommendation said) would have been cosmetic: an attacker builds the Keycloak authorization URL by hand — an authorization request needs no client secret — and the callback still accepted it. So:
- **Server:** the callback requires the signed transaction cookie set by `/api/auth/login`, bound to `state`, else 400 without contacting Keycloak; the OIDC nonce is always checked; the cookie is cleared on every path. The `__Host-oauth_state` cookie was a leftover of the Manus-era callback (which had a real check) that the Keycloak rewrite silently dropped.
- **Client:** `startLogin()` navigates to `/api/auth/login?redirect=<path>`. Multi-origin concern from the original note does not apply: all three front-ends share `client/src/const.ts` (one Vite alias) and one origin, dev servers proxy `/api`, live `APP_URL` is the public origin.
- **Found and fixed on the way:** (a) `/api/auth/login?redirect=<anything>` was reflected into the post-login redirect — an open redirect an attacker can hand a victim; `safeReturnTo()` now allows only a same-origin path (browsers treat `\` as `/` and drop tab/CR/LF, so `/\evil` and `/<TAB>/evil` are refused too) and runs at login AND callback because the redirect suffix of `state` is unsigned; (b) a malformed %-escape in `state` threw outside the try block; (c) **a regression my own fix would have introduced:** `main.tsx` fires `startLogin()` once per *failed query*, so parallel 401s would race to set the cookie and leave one that belongs to a different login than the browser follows — `startLogin()` is now debounced.
**Evidence:** `oauthPkce.test.ts` 10 → 38 tests; running the OLD tests against the fixed server failed exactly the four that pinned the vulnerable behaviour; seven mutations each fail a test (callback proceeds without cookie → 7 failures; cookie not bound to state; nonce unchecked; open redirect ×2; throw outside try; cookie not cleared). `client/src/startLogin.test.ts` (9) pins that the browser never builds a Keycloak URL and that the debounce holds.
**VERIFIED LIVE (deployed as `whatsapp-server:qa-local5`), everything short of typing a password:** the running bundle contains the new guard and the server-driven login URL in all three front-ends and no trace of the dead `__Host-oauth_state` cookie (checked in the running pod, not just the image); `GET /api/auth/callback?code=x&state=y` with no transaction cookie → **400** (before the fix that path reached the token exchange); `/api/auth/login?redirect=https://evil.example` still redirects to Keycloak; and — the check that would have made this an outage if wrong — following the server-built authorization URL to Keycloak returns **HTTP 200 with the login form**, not an "Invalid redirect_uri" page, so `https://wa-app.newfire.app/api/auth/callback` (with PKCE `code_challenge_method=S256`) is registered for client `wacommerce-app`. **NOT VERIFIED:** completing a login with real credentials in a browser — the one step this environment cannot do.

## QA-029 — P1: `recon-worker` panics on real data, and its orphan-repair pass has never been able to run (and I had wrongly closed this as "contention" in QA-010)
**COMPONENT:** `rust/recon-worker/src/main.rs` (two raw-SQL queries against `payment_intents`)
**HOW IT SURFACED:** the final e2e run failed `recon-worker > POST /recon/trigger` with an instant `fetch failed` (not a timeout). The container log showed `thread 'tokio-rt-worker' panicked at src/main.rs:216:54: error retrieving column 4: error deserializing column 4` — and the same panic on the **scheduled hourly run** at 01:31 and again at 02:30. My earlier QA-010 analysis blamed test contention because the test passed in isolation; that was a false inference — it passed in isolation only because `payment_intents` was empty then.
**ROOT CAUSES (both reproduced against the real schema, not inferred):**
1. `status` is the Postgres **enum** `payment_intent_status`. `tokio-postgres` cannot decode a custom enum into a Rust `String`, and `Row::get` **panics** on a decode error. So the reconciliation pass crashed as soon as ≥1 completed/failed intent existed in the last 24 h — i.e. on any real data.
2. The orphan-repair query filtered `status IN ('pending','failed','voided','ledger_drift')`, but `'voided'` and `'ledger_drift'` are **not labels of that enum** (created in migration 0000, never altered). Postgres rejects the whole statement: `ERROR: invalid input value for enum payment_intent_status: "voided"` (reproduced with psql). So the **active repair of orphaned ledger reservations — the safety net that voids stuck pending transfers — has never been able to execute**.
**FIX:** cast `status::text` in both queries; valid labels only (`pending`, `failed`, `cancelled` — the original list minus the two that never existed, plus the clearly non-active `cancelled`); replace panicking `row.get` with `try_get` so an undecodable row becomes a `high` alert / logged skip instead of a crash.
**VERIFIED:** ran the fixed worker locally against the e2e Postgres holding the 5 completed/failed intents that crash the old one: `/recon/trigger` → HTTP 200, 0 panics, "total 5, matched 3", **2 real discrepancies reported** ("completed without ledger tracking" — output that could never appear before), and the repair pass ran for the first time: "repaired orphan pending transfer (voided)" ×2, 2/2 succeeded.
**REGRESSION:** `server/reconWorkerSchema.test.ts` — a static consistency check between the Rust SQL and the real Drizzle enum (every `status IN (...)` label must exist; every selected `status` must be `::text`), with a negative-control fixture of the pre-fix SQL proving it catches both bugs. (Raw SQL in Rust is invisible to `tsc` and to every other test — that is the class of bug.)
**NOT DEPLOYED, ON PURPOSE:** rebuilding the Rust image needs Docker Hub (unreachable from here), and — more importantly — with this fix the repair pass will **execute for the first time ever and void ledger reservations**. It guards against voiding settled transfers (`Ok(false)` = already settled) and the live ledger is currently down so it would be skipped, but a never-before-run money-repair path deserves a human review before it goes to any shared environment. It will flow through CI once pushed. **Live impact is unknown:** the live pod was recreated by my chaos test an hour earlier and had logged no reconciliation run, so I can't say whether live has been panicking.

## QA-031 — P1 → FIXED and wired live: the ledger-bridge's TigerBeetle path had never worked against a real TigerBeetle
**EVIDENCE:** `rust/ledger-bridge` talks HTTP to "a TigerBeetle HTTP sidecar" (`TIGERBEETLE_ADDRESS`). Native TigerBeetle has no HTTP API, and no such sidecar existed anywhere in the repo — the only implementation of the bridge's `/api/v1` contract was the **in-memory test double** `tests/e2e/fixtures/tb-sidecar.mjs`, and the e2e compose ran the bridge with `LEDGER_ALLOW_INMEMORY=true` (a failing TigerBeetle call would have silently fallen back to memory). The live bridge showed TigerBeetle+Postgres unhealthy (QA-022) because nothing was wired — but wiring config alone could never have worked. Building the missing adapter against **real TigerBeetle 0.16.66** found five defects the double structurally could not show:
1. **Flag vocabulary mismatch.** Bridge 4/8/16 (pending/post/void) vs TigerBeetle 2/4/8. Sent unchanged, a *commit* executes as a **void** and nothing is posted, and a *void* becomes `balancing_debit`. Proved by sending the raw flags to a real cluster.
2. **`amount: 0` = "post everything" is false** in 0.16: it posts nothing and consumes the hold (adapter sends `AMOUNT_MAX`).
3. **Failed transfer ids are burned** (`id_already_failed`): an account must exist *before* the first attempt. My first design ("try, create the account, retry") failed on this in the first live run against the real ledger.
4. **Account ids/ledgers disagree.** `/accounts/provision` mints a random id in ledger 700 that the server ignores; transfers use deterministic ids in ledger 1 that nothing creates. Real TigerBeetle rejects transfers to unknown accounts and to mismatched ledgers. (Server `ensureLedgerAccountProvisioned` discards the returned id.)
5. **No overdraft protection.** Accounts carry no flags, so a reserve of ₦10,000 from a never-funded account succeeded and posted (balance −1,000,000 kobo, observed on real TigerBeetle).
**FIX:** `services/tb-adapter` — a real HTTP↔TigerBeetle adapter implementing the bridge's contract (`translate.mjs` pure + `server.mjs` real client): flag translation, `AMOUNT_MAX`, accounts ensured before submit (cached), hostname→IP re-resolution, every call bounded (dead TigerBeetle → 503, not a hang), loopback-only. ## QA-033 — P1: the server↔bridge↔TigerBeetle contract was broken in four ways once tested against a real ledger
**EVIDENCE:** running the money flows against real TigerBeetle (not the in-memory double the e2e stack used, with the bridge's own in-memory fallback ALSO on — so a failing ledger call could not even fail a test) surfaced:
1. `payOverTime`/`microLoans` sent opaque ids (`credit-facility:<id>`) the bridge rejects with HTTP 400, then treated 400/409 as "already posted" — those ledger legs were never recorded. The bridge answers an idempotent replay with 200, never 409.
2. `POST /transfer` is a two-phase RESERVE that TigerBeetle auto-voids after 15 minutes (`pending_timeout_secs`); four server call sites used it as a direct posting. Fixed with an explicit `single_phase: true` mode that posts atomically and journals as committed.
3. The legacy `payment.confirm` settle path (no `ledgerPendingId`) went straight `escrow → merchant` without ever crediting escrow first — with overdraft protection (below) that is correctly refused. Now books the inflow (`customer → escrow`) first.
4. `commit`/`void` used random transfer ids, so a retried commit was a NEW transfer that failed forever as "already posted" (surfaced as `ledger_unavailable`, indistinguishable from an outage). Ids are now deterministic (`commit:<pending_id>` / `void:<pending_id>`); a retry that TigerBeetle recognises as already-done now returns 200. The ledger REFUSING something (409, e.g. overdraft) is now a distinct answer from the ledger being unreachable (503).
**FIX — overdraft protection (there was none):** the server stamps an account KIND into the first two bytes of every derived ledger account id (`server/services/ledgerAccounts.ts`); `services/tb-adapter` reads that stamp when it creates an account and applies TigerBeetle's `debits_must_not_exceed_credits` to escrow/merchant/merchant-wallet accounts (customer accounts stay unconstrained — their money legitimately arrives from outside). Both sides carry the same table; a test fails if they ever drift.
**VERIFIED:** 29 integration tests against a real TigerBeetle (overdraft refusal, holds, idempotent retries, refusal-vs-outage mapping) + 24 new unit tests + 9 Rust tests; the three simulation journeys that pinned the old opaque-id contract were updated and re-verified.

## QA-035 — P1: the webhook confirmation path never committed the TigerBeetle reservation it created — found by the QA-033 real-ledger e2e test itself
**EVIDENCE:** `payment.initiate` reserves funds in TigerBeetle and stores `ledgerPendingId` on the `payment_intents` row. But the actual production confirmation path — `confirmProviderPayment` in `server/services/paymentConfirm.ts`, which is what a real Paystack/Flutterwave webhook calls (as opposed to the admin-triggered `payment.confirm` tRPC mutation, which DOES commit) — marked the intent `completed` in Postgres and created the escrow hold **without ever calling `/ledger/commit`**. `tests/e2e/ledger-money.test.ts`, run against a real TigerBeetle end-to-end (webhook → DB → ledger), caught it directly: after a signed webhook confirmed the payment, the customer's TigerBeetle account still showed `debits_pending: 250000, debits_posted: 0` — the money never actually moved, it just sat reserved until TigerBeetle's own 15-minute timeout would have silently voided it, while Postgres and the customer both believed the payment had succeeded.
**Why nothing caught this earlier:** the ledger was never wired to a real TigerBeetle until this session (QA-031), so there was nothing for this gap to disagree with; and `recon-worker`'s orphan-repair sweep explicitly excludes `completed` intents (`WHERE status IN ('pending','failed','cancelled')`) — it was never going to find this either.
**FIX:** `settleIntentLedger()` in `paymentConfirm.ts` — commits `ledgerPendingId` if present, else books the same inflow-then-settle direct legs as QA-033's `payment.confirm` fix — called on every confirmation path for an intent, including webhook replays. `commit`/`postDirectLedgerLeg` are both idempotent on their key, so calling it repeatedly is always safe (`replayed: true`) and doubles as the retry story: a provider's natural webhook redelivery is what heals a first attempt that hit a transient ledger outage. Never throws — the DB row is already committed and the provider already has the money, so a ledger hiccup logs (critical) rather than failing the webhook response back to the provider.
**VERIFIED:** existing unit suites (`paymentConfirm.w26.test.ts` and 5 others touching this path, 49 tests) still pass unmocked, hitting and correctly swallowing the new (expected, in that context) ledger-unreachable path; re-running `tests/e2e/ledger-money.test.ts` against a real TigerBeetle end-to-end is the actual regression test for this and is where it was caught.
**NOT DONE:** `paymentTransactions`-kind confirmations (the older/parallel table, `kind === "transaction"`) are not covered — that table has no `ledgerPendingId` column at all, so it's unclear whether it's meant to participate in the ledger reservation flow; needs an owner decision, not a guess.

## QA-039 — hardening batch: SSO login CSRF, fail-closed service auth, a button that could only do harm, and a test-isolation bug that hid behind retries
Five items, each with tests that were mutation-checked (a mutation that survives is a test that cannot fail).

**1. Tenant-portal SSO login CSRF (P2 → FIXED, server + browser; NOT browser-verified).** `/portal/sso-callback` completed a portal login for any `code` + `state` in its URL. The `state` it sent out was `btoa({tenantId, returnTo})` — guessable, and stored nowhere, so nothing tied the callback to the browser that started the login. ## QA-040 — overload behaviour: what was measured, a correction to my own earlier finding, and a feature I built and then removed
**My earlier finding was wrong in its emphasis.** `.qa/perf/summary.md` recorded "no load shedding — p99 13.3 s at c=800". That number came from a driver on this laptop reaching the server through Docker Desktop's port proxy, and its worst-case latency (≈20 s) equalled the whole test duration — a few connections starved for the entire run, the signature of the client/proxy path. With the **driver inside the docker network**, closed-loop `auth.me` at c=800 gives **p99 ≈ 0.85–0.95 s, max ≈ 1.0–1.15 s** (runs 4 and 3 of the comparison agree; throughput ~1,250–1,330 rps). The tail is bounded by concurrency ÷ throughput, as it should be: the server degrades gracefully; it does not queue without bound *when clients wait for replies*.

**I then built a load shedder and it did not help; it was removed.** Reasoning at the time: overload is a queueing problem, so refuse work quickly. Implementation: event-loop-lag driven (p99 of `monitorEventLoopDelay` per 500 ms window; proportional shedding from 200 ms to 1000 ms), `503 + Retry-After`, never shedding health, metrics, provider webhooks or internal/scheduled callers; 54 unit tests, 10/10 mutations killed. Then it was measured properly:
- **Closed loop, in-network, ABBA order, no other load on the machine** (run 4): OFF ≈ ON ≈ ON-with-thresholds-that-can-never-fire (the overhead control), all within run-to-run noise (±15 %). One earlier run showed ON at half the throughput; it overlapped my own mutation-test loops on the same CPU and is kept in `.qa/perf/loadshed/` **labelled contaminated** and excluded from every conclusion.
- **Open loop, 2× capacity (2,600 rps offered vs ~1,300), 5,000-socket pool** (run 6, the honest overload test — real users do not slow down when the server does): the queue grows without bound (served p50 7–10 s, p95 31–55 s, p99 ≈ 56 s) **with or without the shedder**, which refused **38 and 1** of ~44,000 requests. Its 503s themselves took ~9 s to arrive.
- **Why:** the queue is *upstream* of any middleware — in the kernel's accept/receive queues and HTTP parsing — so a check that runs after the request has been read cannot bound anything. Effective admission control at that layer has to sit in front of the process (ingress connection and rate limits), or add capacity (the HPA, QA-041).
- **Decision:** removed (revert 0596e93), not shipped, not defaulted off. The tooling that found this stays: `scripts/perf/load.mjs` now has per-status latency (a fast 503 must not flatter the latency of what *was* served) and an open-loop `--rate` mode; `.qa/perf/loadshed-compare.sh` runs an image in-network in ABBA order. The runs are in `.qa/perf/loadshed/` (run 5 is labelled INVALID: with a 200-socket pool the excess queued inside the *client's* connection pool and the server never saw it).
- **Lessons I would otherwise repeat:** closed-loop tests cannot show unbounded queueing and open-loop tests can be silently client-bound; drive load from inside the network; ABBA, not A-then-B; never run anything else on the machine that hosts the Docker VM while measuring; and a first result that flatters a change you just built is a reason to re-run, not to write it down.
- **Still open (measured, not fixed):** under sustained open-loop overload one process has no protection — excess requests wait 10–60 s. Whether the **ingress** in front of `server` limits connections or queue time is **not known** (I did not inspect it); that, plus scale-out, is where this belongs.

## QA-042 — the ledger bridge was down for 30 seconds on EVERY pod termination (found by re-running the chaos experiments on the new topology); plus rollouts that co-located replicas, and tracing that never worked
The pass-2 chaos experiments (CX-01…07) measured `server`. **Nobody had measured the bridge under money traffic.** Re-running chaos on the pass-3 topology, with a probe that drives real `reserve → void` pairs through bridge → adapter → the shared TigerBeetle (`.qa/chaos/ledger-probe.mjs`, run from inside a `server` pod so it uses the pod's own key and never prints it), found three real defects and one measurement trap.

**1. The ledger bridge ignored SIGTERM (P1, money-path availability — FIXED live, before/after measured).**
- **Before:** rolling the bridge under 5 reserve→void/s: **79.9 % availability, 150 failed reserves in one window of exactly 30.0 s** (all `503 ledger_unavailable`), running to ~24 s after Kubernetes called the rollout done. Deleting **one of two healthy replicas** (`kubectl delete pod`, i.e. a drain, an eviction or a scale-down): **72.6 %, the same 30 s window, 150 failures.**
- **Cause:** `with_graceful_shutdown(signal::ctrl_c())` — SIGINT only. Kubernetes sends SIGTERM, and as PID 1 in a container the bridge ignores a signal it has no handler for, so it ran on until SIGKILL at the end of the 30 s grace period. Its `tb-adapter` sidecar (Node) *does* honour SIGTERM and exits within ~3 s. So for ~27 s a live bridge with a dead adapter answered 503 to every client whose keep-alive connection was pinned to it — and `server` holds keep-alive connections. Exactly `terminationGracePeriodSeconds`, and exactly 150 = 30 s × 5/s: that arithmetic is what identified it. **Real payments would have failed with 503 on every bridge rollout or pod loss.**
- **Fix:** `shutdown_signal()` (SIGTERM *or* SIGINT, then drain and exit) in `ledger-bridge`, `recon-worker` and `event-processor` (`hermes-router` already did it right); `preStop` sleeps so the **adapter outlives the bridge's drain** (bridge 5 s — the Service needs a moment to stop sending it new connections — then adapter 10 s; well inside the 30 s grace). **Tests:** the Rust test sends a *real* SIGTERM to the test process, so a missing handler kills the whole test binary (mutation-verified: the wrong-signal mutant is killed by the signal itself); a wiring test that reads only the production half of `main.rs` (the test module contains the strings it searches for); manifest tests pin the ordering (adapter > bridge, ≥ 3 s, fits the grace) with 3/3 mutations.
- **After (same probe, same rate), live:** **A** the patch that rolls in the fixed image — the *old* pods still terminate the old way: 70.4 % (the bug, one last time); **B** `rollout restart`, new pods terminate: **100.000 % (798/798)**; **C** graceful delete of one pod: **100.000 % (698/698)**; **D** *abrupt* delete (`--grace-period=0 --force`): **100.000 % (698/698)**.
- **Not covered:** loss of a whole node; failures on the TigerBeetle side (shared infra, not exercised — the owner has declined force-killing its pods before).

**2. Rollouts co-located the replicas — and my first explanation was wrong (P2 — FIXED live, measured).** After the `server` rollout, both replicas sat on one worker (`scripts/qa-local-ship.sh check-spread` failed, as designed). I attributed it to the 200 m CPU request not fitting on the tighter worker, lowered the request to 100 m, rolled again — and both replicas landed together **again, on the other node.** So that theory was at best incomplete (the request stays at 100 m because actual use is 8–36 m and a smaller request only helps, but it was not the cause). **Actual mechanism:** the spread constraint's `labelSelector` matches pods of *every revision*, so during a rolling update the old pods (one per node) bias the count, the second new pod sees a tie between nodes, and picks by chance. **Fix:** `matchLabelKeys: [pod-template-hash]` on `server` and `ledger-bridge` (counts only same-revision pods). **Measured:** before — 2 of 2 rollouts co-located; after — **3 of 3 `server` rollouts and 3 of 3 bridge rollouts spread across both nodes**, with **1,898/1,898 public requests OK through the three `server` rollouts** (and 1,099/1,099 and 1,098/1,098 through the two earlier ones): zero-downtime `server` rollouts are now measured five times.

**3. The Rust services' traces never reached Jaeger (P3 — FIXED live).** Each Rust service builds its OTLP exporter with `.with_tonic()` (gRPC) but was pointed at the collector's **HTTP** port 4318 (gRPC is 4317). Every export failed with `transport error`, logged at ERROR level with an *empty message* (`BatchSpanProcessor.ExportError`), so nothing else ever failed and nobody noticed — this is the "ledger-bridge never appears as a traced service" I recorded in QA-027 and never chased. **Fix:** port 4317 on all four; a test reads each service's *source* to learn its protocol and checks the manifest's port (3/3 mutations). **Verified live:** 0 export errors in all four; `ledger-bridge` now appears in Jaeger with `tigerbeetle.create_pending_transfer` spans for the first time. The span-derived alert rules that would read them live in the monitoring repo (`docs/handoff/`), not here.

**4. When the link to the host is 23 KB/s, ship the change, not the image.** The cluster host is reached over a Tailscale DERP relay (~3 s round trip, no direct path that evening). Streaming a whole 35 MB image moved 18 MB in 13 minutes. What had changed was two 10 MB binaries and a 15 MB `dist/` — 11 MB compressed. I killed the stuck transfer, uploaded only that, and rebuilt the images **on the host** (Rust: the Dockerfile's runtime stage + my binary; server: the previous image exported from a kind node's containerd + the new `dist/`), re-verifying every artifact **by content on what was actually built** before loading it. 2. **Was write availability actually affected?** Ran the real reserve→void probe (`.qa/chaos/ledger-probe.mjs`) through the live bridge → tb-adapter → TigerBeetle path: **98/98 calls, 100% availability.** Quorum was holding via the other two links (`tigerbeetle-0`↔`tigerbeetle-2` logged zero errors the whole time) — this was a silent, one-link degradation, not an outage.
3. **Network or application layer?** From inside `tigerbeetle-0`'s own network namespace (ephemeral debug container, no restart): raw TCP connect to `tigerbeetle-1`'s then-current IP succeeded instantly, `ping` was sub-millisecond. The underlying pod network between those two nodes was completely healthy — ruled out infrastructure.
4. **First fix attempt (wrong replica): restarted `tigerbeetle-1`** (graceful, no `--force`) on the theory that it held stuck state. New pod came up cleanly, connected to `tigerbeetle-2` immediately — but `tigerbeetle-0` kept failing to reach it, unchanged. Wrong target; recorded rather than hidden.
5. **Found the real cause:** a live packet capture from `tigerbeetle-0`'s network namespace showed it dialing **10.244.2.121** — an IP that belonged to *neither* the pod that was just replaced (10.244.2.125) *nor* the new one (10.244.2.48), and that `kubectl get pods -A -o wide` confirmed was not assigned to anything, anywhere, in the cluster. A fresh DNS lookup of `tigerbeetle-1`'s headless service name, done from `tigerbeetle-2` at the same moment, correctly returned the current IP. **Root cause: `tigerbeetle-0`'s own long-running process (19h uptime) was holding a stale cached peer address from some earlier point in its life and never re-resolving DNS on reconnect** — not a network fault, not a TigerBeetle-1 fault.

**Fix:** restarted `tigerbeetle-0` itself (graceful, no `--force`). Fresh process, fresh DNS resolution: startup log shows `on_connect: connected to=1` and `connected to=2` within 2 seconds of listening — both peers, immediately. **Verified:** 0 `replica = 1` error lines in the 30s after (down from a steady ~20–24 per 30s before, across the whole investigation); 0 pod restarts on any replica (no crash loop, no VSR view-change storm); the reserve→void probe re-run after the fix: 98/98, 100%, same as before — no regression, now on a genuinely healthy 3-of-3 cluster instead of a silently degraded one.

**Why this matters beyond the one incident:** this was invisible to every existing signal. Kubernetes had all three pods `Ready` (readiness probes don't check peer connectivity). Restart counts stayed at 0 throughout (nothing crashed). The money path stayed at 100% (VSR only needs 2 of 3). If `tigerbeetle-2` — the one replica actually carrying quorum with both others — had lost even a few seconds of connectivity for any unrelated reason while this was ongoing, that would have been a full quorum loss with zero warning beforehand. **Follow-up worth raising with the monitoring team (the QA-041 hand-off already covers deployment/pod-level alerts, not inter-replica link health):** a rule on the existing `otel_span_calls_total{span_name=~"tigerbeetle\\..+"}` spanmetrics, or a new one if TigerBeetle's own message_bus doesn't emit spans for peer connection failures — this class of problem produces no span, no restart, no readiness-probe failure, only a log line nobody was watching.

**Left as-is:** an ephemeral debug container (`debugger-hjmzz`) attached to `tigerbeetle-2` during investigation never successfully attached (streamed logs instead) and cannot be individually removed; it is inert and will clear on that replica's next legitimate restart — restarting it solely to tidy this up was judged not worth another touch of shared ledger infra for a cosmetic leftover.

**NetworkPolicy (QA-041) status:** unaffected by any of this — still drafted, not applied. This finding was discovered *while* preparing to apply it, not caused by it; whether to retry the apply now that the cluster is healthy is a separate decision.

## QA-046 — fixing Temporal and Fluvio for real: one genuine fix (Temporal), one fix that surfaced a deeper cluster-level gap no application code can close (Fluvio)
Follow-up to QA-045's findings 1 and 2, done with the user's go-ahead, in increasing order of how far each one could actually go.

**Temporal (P3 — FIXED).** `triggerPaymentSaga` in `server/routers/payment.ts` unconditionally attempted a Temporal connection on every `payment.initiate`, even though — traced fully this time — there is no `paymentSagaWorkflow` anywhere in this codebase for it to run: the one real Temporal worker that exists (`services/temporal-workflows/worker.ts`) registers `TenantOnboardingWorkflow`/`OrderFulfillmentWorkflow`/`InventorySyncWorkflow`/`BroadcastCampaignWorkflow` on task queue `"whatsapp-commerce"`, not `"commerce-engine"` (payment.ts's target), and **isn't deployed anywhere in this cluster regardless** (no k8s-flux manifest, nothing running). So simply fixing the address would have made things *worse*, not better: `client.workflow.start()` would have started succeeding — creating a workflow execution that sits in Temporal forever, since no worker can ever pick it up — trading today's honest "fails fast, falls back synchronously" for a silently-stuck execution that looks durable and isn't. **Fix:** guarded the same way `onboarding.ts` already guards its own Temporal call — skip cleanly when `TEMPORAL_ADDRESS` is unset, no more doomed connection attempt on every real payment. The file's own "ATOMICITY GUARANTEES" header comment overstated both this and Fluvio as live; corrected. Verified: `tsc` clean, the 4 payment-related test files (90 tests) plus a full regression (291 files, 4,418 tests) pass unchanged, and the real end-to-end payment test in QA-045 finding 5 already lived evidence of this (`sagaWorkflowId: null`).

**Fluvio (P2 — application-level bugs fixed and verified; blocked on a cluster-level gap outside this repo).** Three real, independent bugs, found by tracing all the way to root cause rather than stopping at the first plausible one:
1. **Wrong protocol.** `fluvio-consumer`'s poll loop hit a REST API (`GET {sc}/topics/:name/records`) that `fluvio-sc` has never implemented — confirmed earlier (QA-045) via its own logs accepting and closing the connection on its *native* `FluvioApiServer` protocol on that same port. The `fluvio` SDK crate was already a declared dependency, `optional = true` behind a `fluvio-enabled` Cargo feature the Dockerfile's `cargo build --release` never passed — so it had never actually been compiled in. **Fixed:** made it a required dependency and rewrote the consumer loop against the real SDK (`Fluvio::connect_with_config` → `consumer_with_config` → `Stream::next()`), one task per topic with its own backoff/retry; added a real `/produce` HTTP endpoint using the same SDK's producer API, closing the matching gap on the publish side (`payment.ts`'s `publishPaymentEvent` posted to a `/produce` route that didn't exist at all — every call 404'd, silently swallowed).
2. **Wrong topic names.** Live test against the real cluster: `Invalid topic name: topic name may only include lowercase letters (a-z), numbers (0-9), and hyphens (-)`. The five `wacommerce.*` names (dotted, copied from the Kafka side of the codebase, which does allow dots) were never valid Fluvio topic names — full stop, not just "not yet created." **Fixed:** renamed to `wacommerce-orders` / `wacommerce-payments` / `wacommerce-conversations` / `wacommerce-inventory` / `wacommerce-hermes-po` throughout (consumer, docs). Also fixed `payment.ts`'s `publishPaymentEvent`, which had been sending the *event name itself* ("payment.initiated", "payment.failed", …) as the topic — invalid for the same reason, AND not one of the five topics the consumer was ever listening to even before that. It now always publishes to the fixed `wacommerce-payments` topic with `eventType` carried inside the payload.
3. **Topics never provisioned.** Even with valid names, none of the five existed in this Fluvio cluster. Added `services/fluvio-consumer/src/bin/provision_topics.rs` (idempotent — skips what already exists) and ran it against the live cluster: all five now exist, confirmed via `FluvioAdmin::list`.

**What's still blocked, and why it's not this repo's to fix:** with all three of the above corrected, both consuming and producing still hang — traced with a purpose-built, watchdog-timed diagnostic binary run *inside* the cluster (no port-forward, so cross-namespace routing wasn't a confound): `Fluvio::connect_with_config` returns in ~3ms (a control-plane-only connection to the SC) and `FluvioAdmin::list` of topics returns in ~45ms, but `consumer_with_config` (consume) and `topic_producer` (produce) never resolve — because **this Fluvio cluster has zero SPUs (Streaming Processing Units) registered**, confirmed by listing them directly (empty). The SC can create and list topics (control-plane only) but there is no data-plane component for any client, from any namespace, to actually read or write through. This is a gap in how the `fluvio` namespace's cluster was deployed, not in `fluvio-consumer`'s code, and shared infrastructure this repo doesn't own — same category as the TigerBeetle namespace (QA-041) and the Kafka cluster naming (both shared, owned elsewhere). **Made the code honest about this rather than silently hanging:** both the consumer stream open and the two producer operations are now wrapped in a 15s timeout with a clear log message naming the real cause ("no SPU available to route this topic"); the consumer loop's existing capped-exponential backoff (2s → 30s) means this now fails loudly and infrequently instead of the old behavior's ~5s-forever hot loop. The moment someone registers a working SPU for this cluster, everything above starts working with no further code changes — verified as far as that boundary, not beyond it.

**Shipped:** built and deployed live (see readiness/deployment notes for the image tag); regression suite unaffected (Rust-side changes, no TypeScript test coverage of this service; `cargo build --release` clean, `cargo check` clean).

## QA-047 — the Fluvio SPU gap, closed: two real cluster-deployment bugs, not one, and full end-to-end proof
Follow-up to QA-046's "not this repo's to fix" finding — the user confirmed the `fluvio` namespace is also theirs, so it became this repo's to fix after all. Traced to full resolution, not just diagnosed.

**Bug 1: the SPU's persistent-volume storage class doesn't exist on this cluster.** The `spu-k8` ConfigMap (which `fluvio-sc` reads when provisioning a new SPU StatefulSet in Kubernetes mode) had `"storageClass":"rook-ceph-block"` baked in from the Helm chart's default values — a Ceph-backed class that makes sense on a bare-metal cluster with Rook installed, but this is a `kind` cluster, whose only StorageClass is `standard` (`rancher.io/local-path`). Any SPU pod the SC tried to create would have had an unbindable PVC forever. **Fixed:** patched the ConfigMap's `storageClass` to `standard`. No SC restart needed — it reads the ConfigMap fresh when provisioning, confirmed live in its own logs (`storage_class: Some("standard")`) within seconds of the patch, no code change. Then created the `SpuGroup` custom resource (`kubectl apply`, 1 replica — matching everything else's single-node scale here) that had never existed at all; the SPU pod (`fluvio-spg-main-0`) came up clean, PVC bound instantly, 0 restarts.

**Bug 2: the SPU has no external ingress configured, and the client wasn't told to use the in-cluster address instead.** Even with a healthy SPU registered, both consuming and producing still hung. Traced with `kubectl get spus.fluvio.infinyon.com -o yaml`: `publicEndpoint.ingress: []` — genuinely empty, no host at all, so any client using the default (external-facing) address gets `can't connect to :9005` and hangs on DNS resolution of an empty hostname. But the same object also carries `publicEndpointLocal.host: fluvio-spu-main-0.fluvio.svc.cluster.local` — a fully-qualified, cross-namespace-reachable in-cluster address that was sitting right there, unused. The `fluvio` SDK has a config field for exactly this situation, `FluvioClusterConfig.use_spu_local_address`, defaulted to `false`. **Fixed:** set it to `true` in `fluvio-consumer`'s cluster config — correct for this deployment specifically because every real caller is itself in-cluster (a different namespace, but still in-cluster); this is not a workaround, it is what that field is for.

**Verified completely, twice.** First inside the cluster with a purpose-built test binary (no port-forward): all 5 topics went from a 20s watchdog timeout to `consumer_with_config` returning immediately. Then a full real round trip: `POST /produce` → `200 {"ok":true}` → the record landed in Fluvio's own storage → the consumer read it back at **offset 0** (the topic's first-ever message) → forwarded the exact payload to the platform target. Shipped live (`qa-local2`): the deployed pod's own startup log shows all 5 topics `"consumer connected, waiting for records"` within 50ms of boot, `/health` reports `fluvio_connected:true`, 0 restarts, 0 warnings/errors in the minutes since.

**What this means for the two other findings that used Fluvio as their example of "genuinely unused":** QA-045's Fluvio finding and payment.ts's corrected header comment ("Fluvio — NOT LIVE") are now stale in the best possible way — superseded by this entry. `publishPaymentEvent`'s fixed topic name and payload shape (QA-046) will now actually reach a live consumer.

## QA-048 — does a merchant actually get provisioned in Medusa, Odoo and Twenty? Stood up real local instances of all three and ran the real adapter code against them, not mocks
Prompted by a direct question: has this engagement ever tested the bring-your-own ERP/CRM provisioning path (`server/services/erpProvision/`) against a real Medusa, Odoo or Twenty instance? It hadn't — every prior pass either read the code or relied on the existing test suite, which is deliberately mock-only by design (`MockMedusaAdapter`/`MockOdooAdapter`, `MEDUSA_ADAPTER=mock`; the file header on the Medusa adapter says outright that "tests and the simulation never hit a live endpoint"). A green mock-backed test suite proves the adapters satisfy their own interface, not that the interface matches what the real vendor API actually expects. So: stood up a real Odoo 17, a real Twenty CRM (latest), and a real Medusa v2 via Docker, and imported the actual, unmodified production classes (`JsonRpcOdooAdapter`, `HttpMedusaAdapter`) and the actual `twentyConnector` GraphQL query/mutation strings from `erpProvision/connectors.ts`, then ran them for real. Found five genuine bugs, all with live before/after reproduction; fixed four, left one as an open architectural gap since it needs a design decision, not a patch.

**Odoo (`server/services/odoo/adapter.ts`) — 2 bugs, both fixed.**
1. `OdooRpcError` discarded Odoo's actual error detail. Odoo's JSON-RPC error shape is `{error: {code, message: "Odoo Server Error", data: {name, message, ...}}}` — the top-level `message` is *always* the same generic string; the real cause lives in `error.data.message`, which the adapter never read. Every Odoo failure surfaced to the platform as "Odoo Server Error" with no way to tell a validation error from an auth failure from a missing field. **Fixed:** now appends `data.message` (or `data.name`) to the thrown error when present.
2. `createInvoice` passed `currency_id: input.currency` — an ISO code string like `"NGN"` — directly into `account.move.currency_id`, which Odoo requires as the numeric `res.currency` record id. Confirmed live: with the raw string, Odoo either rejects the create or silently coerces it wrong depending on version. **Fixed:** added `resolveCurrencyId()`, which searches `res.currency` by ISO `name` and caches the result per adapter instance; `createInvoice` now resolves before creating. Re-ran the full real flow (`authenticate` → `createPartner` idempotency check → `createInvoice`, with a real NGN invoice) against the live Odoo instance after the fix: all four calls succeeded.

**Twenty CRM (`server/services/erpProvision/connectors.ts`'s `twentyConnector`) — 2 bugs, both fixed. Provisioning was 100% broken, not degraded — every single call failed.**
1. Wrong endpoint. `twentyGraphql()` posted to `${cfg.baseUrl}/api`. Confirmed against a live Twenty instance: `/api` doesn't exist (`404 Cannot POST /api`). The real workspace GraphQL endpoint is `/graphql`.
2. Wrong mutation argument name. Even pointed at `/graphql`, `createCompany(input: { name: $name })` fails with `"Argument not allowed: input"` — live schema introspection (`__type(name: "Mutation")`) shows the real argument is `data`, not `input`. **Fixed both**, then re-verified the exact corrected query and mutation strings now in the file directly against the live instance: `FindCompany` returns real data, `CreateCompany` with `data:` creates a real company record and returns its id.

**Medusa (`server/services/medusa/adapter.ts`'s `HttpMedusaAdapter`) — 1 bug fixed (also 100% broken beforehand), 1 open architectural gap.**
1. Wrong auth scheme entirely. The adapter sent `x-medusa-access-token: <key>` on every call — Medusa v1's header. Medusa v2 removed it. Confirmed by the live server's own error message when the wrong scheme was tried: a secret key sent as `Authorization: Bearer <key>` gets rejected with *"A secret API key was passed as a Bearer token. Secret API keys must be sent using HTTP Basic authentication instead."* The correct form (confirmed working) is `Authorization: Basic <raw-key>` — the raw key as-is, not base64-encoded, not paired with a username. **Fixed.** Re-ran `testConnection()` and `listProducts()` against the live instance after the fix: both now succeed for real (`ok: true`; 4 real seeded products returned with real ids).
2. **Open — `createOrder()` calls `POST /admin/orders`, which does not exist in Medusa v2.** Confirmed live: `404 Cannot POST /admin/orders`. Medusa v2 replaced v1's single-call admin order creation with a fundamentally different model — orders are created either through the customer-facing cart/checkout flow (`/store/carts/...`) or via an admin draft-order that's then converted (`/admin/draft-orders` → `.../convert-to-order`), both multi-step, both needing a resolved region/sales-channel/shipping-method the current `MedusaOrderInput` shape doesn't carry. This is not a one-line fix like the other four — it's a different integration pattern, so it's left open pending a decision on which flow this platform should use, rather than guessed at. **Practical impact right now: `getMedusaAdapter(tenantId)` returns `null` for every tenant in the live deployment already (QA-133/earlier finding — no `MEDUSA_API_URL`/tenant mapping configured anywhere), so this gap has zero live blast radius today; it only becomes reachable the day a merchant's Medusa credentials are actually wired up.**

**Method note, since this differs from most of this engagement's testing:** SSRF guard (`assertSafeOutboundUrl`, already covered by QA-016) correctly rejects `localhost`/private IPs by design — including in local test setups. Rather than weaken it, the local Docker test instances were addressed via `127.0.0.1.nip.io` (a real, public wildcard-DNS hostname that resolves to `127.0.0.1`) — the same DNS-rebinding shape the guard's own header comment already documents as out of scope for a synchronous hostname check, and a legitimate stand-in for "merchant supplies a real hostname" in production. This means the guard itself was exercised as-is, not bypassed.
**VERIFICATION:** `NODE_ENV=test npx vitest run server/erpProvision.test.ts server/odooB2B.test.ts server/services/odoo/odooWhatsApp.test.ts server/services/medusa/medusa.test.ts` — 72/72 pass unchanged after all four fixes (mock-backed suite is unaffected by real-adapter changes, as expected). Scratch test scripts and local Docker test infrastructure (Odoo, Twenty, Medusa + Postgres + Redis containers) removed after use; nothing was written to any shared/live database — verified the local Postgres port was actually a different, unrelated project's container before any DB write was attempted, and used direct-adapter instantiation (bypassing DB lookups entirely) for Odoo and Medusa; Twenty's fix was verified via direct HTTP reproduction of the exact query/mutation strings rather than a DB-backed run, after the local Postgres turned out to be unusable for this purpose.

## QA-049 — the portal doesn't use the code QA-048 tested. It uses a second, parallel Medusa/Twenty/Odoo client — with its own, independent set of bugs
While checking whether the tenant portal (`client/src/pages/IntegrationsSettings.tsx` — "tenant-admin management of the Medusa / Twenty / Odoo integrations", the actual UI a merchant uses) reflects real connection status, found it doesn't call any of the code QA-048 just fixed at all. **Medusa (`MedusaClient`) — 3 bugs, all fixed.**
1. Same root cause as QA-048: `Authorization: Bearer ${apiKey}` — v2 rejects it the same way, confirmed live with the same server-side error naming Basic as the required scheme. **Fixed** identically.
2. New: `upsertProduct`'s create path 400s live — *"Product options are not provided for: [...]"*. ## QA-061 — the delivery-PIN buyer-protection system was fully built and end-to-end wired, except for its own entry point: nothing ever created a shipment for a chat-originated order
**SEVERITY:** P1 (High) — a real, load-bearing money-safety mechanism (buyer must hand a PIN to the rider before the merchant gets paid) never actually activated for any delivery order
**COMPONENT:** `server/services/paymentConfirm.ts` (new `ensureDeliveryShipment`), `server/services/receipts.ts` (`sendOrderReceipt`)
**EVIDENCE:** User asked "why is the 18,000 held in escrow" then "how does the buyer confirm delivery." Live-traced a real paid order (`ORD-MUI6R00Y`, `fulfillment: "delivery"`) and found its escrow row had `shipment_id: null` — no shipment existed at all, so no delivery PIN had ever been generated. Tracing the delivery-PIN system found it fully built end-to-end (`generateDeliveryPin`/`hashDeliveryPin`/`verifyDeliveryPin` in `logistics.ts`, `assertDeliveryPinAllowed` gating the "delivered" transition, `receipts.ts`'s own message builder already had a `deliveryPin` slot ready to display one) — but the ONLY code path that creates a `logisticsShipments` row (`logistics.createShipment`) is a heavy Shipbubble-style booking mutation requiring structured sender/recipient address data chat checkout never collects, and has **zero UI callers anywhere in the client** (confirmed: grepped for it, zero references). The entire mechanism was correctly built and then never given an entry point for the chat-commerce flow this platform actually runs.
**IMPACT:** Every delivery-fulfillment order placed via chat had NO buyer-protection PIN, NO way for a merchant to ever legitimately mark it delivered through the PIN-gated flow, and — per this session's own earlier finding — no path to the shorter delivery-confirmed release window at all; every such order was silently relying on the 24h blanket auto-confirm timer as its ONLY release mechanism, with the PIN's physical-handoff verification never in play.
**RECOMMENDED FIX / STATUS:** ✅ Fixed and shipped live (`qa-local48`). New `ensureDeliveryShipment(db, orderId, tenantId)` runs right after payment confirms (before the receipt sends): for orders with `metadata.fulfillment === "delivery"` and no existing shipment, creates a lightweight `logisticsShipments` row (every field it touches beyond `orderId`/`tenantId` is nullable in the schema — confirmed before relying on it) with a freshly generated, immediately-hashed PIN (`hashDeliveryPin`, same convention as the heavier `createShipment` path). `sendOrderReceipt` gained an optional `freshPin` parameter so the SAME message the buyer already gets right after paying now includes the PIN — the DB only ever stores the hash, so passing the plaintext through at generation time is the only way it can ever reach the buyer for a newly-created shipment. Full unit suite + full 486-journey suite clean (existing `deliveryPin.test.ts`/`receipts.test.ts` unaffected — additive, no signature change to existing callers).
**Why:** a feature can be 100% correctly built and still be completely inert if nothing ever calls its entry point — this is the second time this exact shape of bug has shown up this session (menu-builder's push-to-WhatsApp tool has no UI caller either, though that one is flagged as a scoping decision rather than fixed).
**How to apply:** the heavier `createShipment` (real Shipbubble courier booking, structured addresses) is still genuinely unreachable from any UI — worth a follow-up decision on whether a real dispatch/logistics UI should exist, separate from this lightweight auto-shipment fix.

## QA-063 — Conversation timeline header showed "Invalid Date" — a field name that never existed on the real data, masked by `as any`
**SEVERITY:** P3 (Low) — cosmetic, only became visible once QA-060 fixed the message thread itself (previously nobody could see the header clearly because the whole panel was stuck on the "could not be loaded" fallback)
**COMPONENT:** `client/src/components/ConversationTimeline.tsx`, `client/src/pages/Conversations.tsx`
**EVIDENCE:** User screenshot, right after QA-060 shipped: the real message thread now rendered correctly, but "Invalid Date" appeared next to "12 msgs" in the header. `ConversationTimeline`'s `Conversation` type declared `lastMessageAt: Date | string`, rendered as `new Date(conversation.lastMessageAt).toLocaleString()` — but `db.getConversations` (real data source since QA-056 BUG-01/02) never returns a field with that name; it returns `updatedAt`. **Why:** an `as any` cast at a component boundary doesn't just silence one warning — it deletes TypeScript's ability to catch every future mismatch on that boundary, including a field that was renamed on one side and not the other.
**How to apply:** `selectedConv`'s `useState<any>` in `Conversations.tsx` is a bigger, pre-existing type-safety gap this fix didn't address (out of scope for a one-line cosmetic bug) — worth a real `Conversation` type if this file gets touched again.
