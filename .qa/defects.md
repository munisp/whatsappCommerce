**SEVERITY:** P3 (Low) — audit-integrity gap, not a data-access breach
**COMPONENT:** `server/routers/b2b.ts:162-172` (`approvePurchaseOrder`)
**EVIDENCE:**
```ts

  .input(z.object({ id: z.string(), approvedBy: z.string() }))

    ...
```

`approvedBy` is taken verbatim from client input rather than derived from `ctx.user.id`/`ctx.user.name`. **IMPACT:** Undermines non-repudiation on a procurement-approval audit trail — low severity since it doesn't grant unauthorized access (the tenant/role gate is intact), but it means the `approvedBy` field cannot be trusted as evidence of who actually clicked approve.
**RECOMMENDED FIX:** Derive `approvedBy` from `ctx.user.id`/`ctx.user.name` server-side; drop it from the input schema.
**STATUS:** ✅ FIXED. `approvedBy` removed from the input schema; the mutation now sets `approvedBy: String(ctx.user.id)` derived from the authenticated session (`server/routers/b2b.ts:162-172`), matching the pattern already used for `writeAuditLog` actor fields elsewhere (e.g. `escrow.ts`). ## QA-005 — Trade-credit facility approval/modification bypassed the finance-role gate; any tenant staff member (including read-only "analyst") could extend or freeze real credit exposure
**SEVERITY:** P1 (High) — real financial-exposure authorization gap, matches a failure mode the codebase's own security model (W46) was explicitly built to close elsewhere, but this router was missed
**COMPONENT:** `server/routers/tradeCredit.ts` — `createAccount`, `updateAccount`, `setAccountStatus`, `approveAccount`, `recordRepayment`
**EVIDENCE:**
- `server/services/capabilities.ts` header (W46 kyc / TEN-9), quoted verbatim: *"The 3-role model (owner/operator/analyst) let ANY operator move money."* — describing exactly the bug class this fix exists to prevent — and: *"moneyProcedure + assertMoneyAccess admit the scoped 'finance' role; 'catalog'/'analyst' can NEVER move money."*
- `assertTenantAccess` (`server/_core/trpc.ts:146-164`) checks only tenant **membership** (any role) — it has no role-level check at all. Confirmed by reading its full body: admin bypass → `user.tenantId === tenantId` → `user.memberships.includes(tenantId)` → FORBIDDEN. No `membership.role` check anywhere in that function.
- All 5 procedures above call bare `assertTenantAccess(ctx.user, input.supplierTenantId)` before creating a facility with a real `limitCents`, activating a pending facility, changing its limit/terms, freezing/closing it, or recording a repayment against the outstanding balance — meaning an "analyst" (read-only-intended) or "catalog" (product-only-intended) membership at the supplier tenant could call any of these directly via tRPC and it would succeed.
- Compare to `escrow.ts confirmDelivery`, which was hardened for precisely this reason (its own comment: *"an ANALYST membership is not enough (owner|operator or admin; assertTenantAccess was role-agnostic)"*) — that fix was never applied to this router.
- The router's own header comment claimed *"every procedure is gated by assertTenantAccess"* and described only tenant isolation, never role scoping — confirming this wasn't a typo/oversight in one call site but the file's original design predating the W46 capability model.
**IMPACT:** A compromised or careless low-privilege staff account at a supplier tenant (analyst/catalog role — roles explicitly documented elsewhere as forbidden from money movement) could open a credit line to a buyer, raise an existing limit, unfreeze a suspended facility, or record a fabricated repayment, all without ever touching the money-gated procedures the rest of the platform relies on.
**FIX APPLIED:** Swapped `assertTenantAccess` → `await assertMoneyAccess` (owner|operator|finance only) on the 5 supplier-side procedures that create/modify real exposure. Left buyer-side self-service procedures (`requestAccount`, `requestMandate`, `confirmMandate`, `revokeMandate`, `initiateRepayment`) on `assertTenantAccess` — those act on the caller's own tenant's exposure, not a counterparty's, and over-restricting them wasn't verified as necessary or safe in the time available; flagging `initiateRepayment` in particular as a lower-priority candidate for the same treatment if you want full consistency, since it does move money (charges a mandate / creates a payment link), just in the safer direction (paying down debt, not creating it).
**REGRESSION:** Found 2 tests in `server/tradeCredit.kybGate.test.ts` broke on the fix — not because the fix was wrong, but because that test file's `fakeDb()` mock answers every table query with the same in-memory array, so `assertMoneyAccess`'s new `tenant_memberships` lookup was misanswered with an unrelated KYC row. Fixed by mocking `getMembership` to return `null` (the correct "no membership row, fall back to the legacy `users.tenantId` shortcut" case, matching what that test fixture already models). All 8 related test files (138 tests) pass; `authzCoverage.test.ts`'s ratchets (guard-count ≥115, scanned-procedure count ≥630) still hold — `assertMoneyAccess(` is already recognized as a valid guard by that scanner's generic `assert\w*Access\(` pattern. `tsc --noEmit` clean. Full-suite regression re-run in progress to confirm no other breakage.
**STATUS:** ✅ Fixed, verified on targeted + related suites AND full regression (261/261 files, 3929 passed/7 skipped/0 failed).

## QA-007 — Gift-card `adjust` had no real idempotency protection, contradicting the file's own documented invariant and every sibling money path in the same file
**SEVERITY:** P2 (Medium) — real double-application risk on retry, bounded by this being a manual/back-office tool rather than a high-frequency automated flow
**COMPONENT:** `server/services/giftCards.ts` `adjustGiftCard` (called by `server/routers/giftCards.ts` `adjust`, the same procedure fixed for role-scoping in QA-006)
**EVIDENCE:**
- File header doctrine, quoted verbatim (`server/services/giftCards.ts:9-11`): *"every money-moving leg writes a gift_card_transactions row whose idempotency_key is UNIQUE — the insert IS the exactly-once claim, so webhook replays / chat retries never double-credit or double-debit."*
- Confirmed the unique index is real: `drizzle/schema.ts:6063` `uniqueIndex("gift_card_tx_idempotency_uidx").on(t.idempotencyKey)`.
- Every OTHER money-moving function in this exact file derives a **deterministic** key tied to the underlying transaction: `purchaseGiftCard` → `` `giftcard-purchase:${reference}` `` (line 132), `redeemGiftCard`/checkout path → `giftCardRedeemKey(orderId, code)` (deterministic, lines 330/350), `issueGiftCard` → `` `issue:${id}` `` (line 427).
- `adjustGiftCard` (the odd one out) generated `` `adjust:${crypto.randomUUID()}` `` — a **fresh random value on every call** (was at line 497 before the fix). This makes the unique index structurally incapable of catching a duplicate: two calls with identical `{tenantId, code, deltaCents, note}` (e.g. a network-timeout retry, or a double-click in the admin portal) get different random keys, both inserts succeed, and `balance_cents` is incremented/decremented twice.
**IMPACT:** A retried or double-submitted manual gift-card adjustment silently applies the delta twice — no error, no rejection, the exact failure mode the file's own doctrine comment says should be impossible.
**FIX APPLIED:** `adjustGiftCard` now accepts an optional `idempotencyKey` (threaded through from a new optional `idempotencyKey` field on the router's `.input()`, mirroring the existing pattern in `escrow.ts createHold`/`requestWithdrawal`). When supplied, a matching existing `gift_card_transactions` row short-circuits the whole mutation and returns the current (already-adjusted) balance instead of re-applying — checked inside the same row-locked transaction as the balance update, so it's race-safe. When NOT supplied, behavior is unchanged from before (random key, no protection) — deliberately not inventing an unsafe default, since two *legitimately* distinct adjustments could coincidentally share the same `{tenantId, code, deltaCents, note}` and a content-based default key would wrongly dedupe them. This puts the same tool in callers' hands that `escrow.ts` gives its callers; closing the gap fully would mean deciding whether the admin-portal UI should always generate and resend a stable key per submit action, which is a UI-side follow-up, not a server-side one.
**VERIFICATION:** `tsc --noEmit` clean. **Not** covered by a new automated test — this function uses raw `sql` tagged-template `tx.execute()` calls inside `db.transaction()`, a style with no existing unit-test mocking pattern in this repo (grepped for one, found none), and a mock couldn't prove the real unique-constraint collision behavior this fix relies on anyway (that needs a live Postgres). Flagging as a good candidate for `scripts/pg-integration-money-paths.ts` or the dockerized e2e suite once real infra is available — logged as a testing gap, not silently skipped.
**STATUS:** ✅ Fixed (code + typecheck verified); integration-level proof deferred to when Postgres/Docker is available.

## QA-008 — `scripts/run-e2e.sh` crashes immediately on macOS with `--no-ml` (or with no extra vitest args): "unbound variable"
**SEVERITY:** P2 (Medium) — the canonical e2e entry point (`docs/E2E.md` calls this "Running — Docker path (canonical)") was unusable on macOS in its documented `--no-ml` form, and would also have broken on the plain default invocation with no trailing vitest args
**COMPONENT:** `scripts/run-e2e.sh`
**EVIDENCE:**
- Reproduced directly: `scripts/run-e2e.sh --no-ml` failed immediately at the `docker compose build` step with `scripts/run-e2e.sh: line 62: PROFILES[@]: unbound variable`.
- Root cause: the script has `set -uo pipefail` (line 12). `PROFILES=()` when `--no-ml` is passed (line 18 default `WITH_ML=1` → `PROFILES=(--profile ml)`; `--no-ml` sets `WITH_ML=0`, leaving `PROFILES` empty). `"${PROFILES[@]}"` on an **empty** array under `set -u` throws "unbound variable" on bash ≤4.3 — confirmed the system `/bin/bash` here is `3.2.57(1)-release`, Apple's frozen build (GPLv2 licensing freeze since ~2007; never upgraded past 3.2). The bug was fixed in bash 4.4 (2016), so this only manifests on macOS's default shell, not Linux CI runners — which is presumably why it was never caught.
- Same pattern present a second time: `VITEST_ARGS` (line 20) also starts as `()` and stays empty on any invocation with no trailing `-- <args>` (i.e. the plain, most common invocation `scripts/run-e2e.sh` or `scripts/run-e2e.sh --no-ml` with nothing after) — `"${VITEST_ARGS[@]}"` at the two `vitest run` call sites (then lines 117/120) would have hit the identical crash one step later even after fixing the first occurrence.
**IMPACT:** Anyone running the documented canonical e2e command on a stock macOS machine (no custom bash install) gets an immediate, confusing crash with no useful error about *why* — `docker compose build` never even starts. This is exactly the path this session needed to actually exercise the funds-flow concurrency invariants.
**FIX APPLIED:** Standard bash 3.2-safe idiom for "expand an array that might be empty under `set -u`": `${ARR[@]+"${ARR[@]}"}` instead of `"${ARR[@]}"`. Applied at all 4 call sites (`PROFILES` ×2, `VITEST_ARGS` ×2). `bash -n` confirms valid syntax; behaviorally identical to the original on a modern bash (Linux CI unaffected either way).
**STATUS:** ✅ Fixed.
